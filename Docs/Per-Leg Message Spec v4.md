# Birthmark Protocol — Per-Leg Message Specification

Sep 25, 2026 · @Samuel Ryan

## Purpose and status

This spec is the single source of truth for every message in the revised Birthmark Protocol.&#32;

- **Status:** draft v1. It incorporates every change listed in Changes and open decisions (A1–A23).
- **Where it lives:** `Docs/` in the Birthmark-Standard/Protocol repo, referenced from the paper in one line. It does not count toward TOPS pages.
- **Where it came from:** the revised paper (paper.pdf), the repo's `crypto_legs.py` (byte sizes) and `ProverifModels/`. Where these disagree, this spec records the decision and lists the fix in *Changes and open decisions*.
- **Performance figures:** estimates only, from Appendix B's published-benchmark method. The Raspberry Pi prototype in \[4\] is not representative and is not used.

**Notation.** `||` = concatenation. `ECIES(pk; m)` = randomized IND-CCA2 public-key encryption. `AEAD(k; m)` = AES-256-GCM. `Sign(sk; m)` = Ed25519. `RSign(R; m)` = unlinkable 1-of-n ring signature over ring R.

## Parties and keys

Every key has one purpose. No key is used both to decrypt and to sign, and no node uses one key for two roles.

| Party | Key | Type | Purpose | Public part known to |
| --- | --- | --- | --- | --- |
| Device | cred\_D | secret credential | Proves membership to its validator | Validator (key table), no one else |
| Device | key\_ref | identifier | Tells the validator which key-table entry to use | Validator |
| Validator V | V-token\_sk / pk | ECIES | Decrypts the device token | Devices (provisioned) |
| Validator V | V-sign\_sk / pk | Ed25519 | Signs approvals only (**new, A3**) | C, gatekeepers, revocation registry |
| Validator V | V-transit\_sk / pk | ECIES | Terminates the C→V leg | C |
| Credential processor C | C-device\_sk / pk | ECIES | Relay terminus for the credential packet | Devices (device table) |
| Credential processor C | C-ring\_sk / pk | ring member key | Member key in ring R for signing PacketHash | Gatekeepers, F, I (as part of R) |
| Gatekeeper G\_k (k = 1..3) | Gk-term\_sk / pk | ECIES | Terminates the C→G\_k leg | C |
| Gatekeeper G\_k | Gk-sign\_sk / pk | Ed25519 | Countersigns board postings | F, I |
| Content server F and I | F-device\_sk / pk | ECIES | Relay terminus for the content packet | Devices (device table) |
| Content server F and I | F-id\_sk / pk | Ed25519 | Signs registry submissions (**split, new**) | Registry |
| Every submission server S | S-transit\_sk / pk | ECIES | Terminates every transit leg addressed to S, whatever role S holds in that transaction (Addressed hop, Random hop, C, F or I) | Every other submission server (full transit-key table) and every device (device table) |

**Transit keys belong to servers, not roles.** A, B, C, D, E, F, G, H and I are per-transaction roles, and any submission server can hold any of them, subject to the role rules. Each server therefore holds one transit key pair and a full table of every other server's transit public key. "A-transit", "C-transit" and so on in the leg table mean the S-transit key of whichever server holds that role. The V→C leg also uses C's S-transit key, so validators hold the transit-key table too (OD12, resolved).

**Per-transaction values** (generated by the device, never reused):

- `n`: 128-bit content nonce. Goes only to F and I.
- `tx_nonce`: 128-bit replay nonce. Goes only to V, inside the token.
- `BK` (BlindShare\_key): 256-bit AEAD key. Generated by the **device** (**changed, A1**). Goes to C, then to the gatekeepers.

**Ring R** (A4): the ring public keys of the C-candidate pool **minus the three currently active gatekeepers**. Verifiers check against the ring that is current at verification time. Ring keys are separate from every other node key. In the simulator the pool has 17 nodes, which makes σ\_C 576 bytes.

## Device-side construction

The device builds one credential packet and two content packets per transaction. It then wraps each for its first relay hop. The binding change (A1) is steps 4–7: the device, not C, creates the blinded commitment and seals it inside the token.

1. `ContentHash = SHA-256(candidate image)`. A candidate image is the RAW file, the ISP-processed image, or an adjusted version that clears the deviation threshold (see open decision OD1).
2. `n` ← 128-bit random.
3. `PacketHash = SHA-256(ContentHash || n)`.
4. `BK` ← 256-bit random.
5. `EncPH = AEAD(BK; PacketHash)`. This is 48 bytes (32 + 16-byte tag). A fixed AEAD nonce is safe because BK is single-use.
6. `tx_nonce` ← 128-bit random.
7. `Token = ECIES(V-token_pk; cred_D || tx_nonce || EncPH)`. With a 32-byte cred\_D this is 145 bytes (previously 81).
8. `P_C = ECIES(C-device_pk; Token || key_ref || PacketHash || BK)`.
9. `P_F = ECIES(F-device_pk; ContentHash || n || mod_level || [h(metadata)])`, and `P_I` the same under I-device\_pk.
10. First-hop wraps: `Cred-1 = ECIES(A-transit_pk; rc_C || P_C)`, `ContA-1 = ECIES(D-transit_pk; rc_F || P_F)`, `ContB-1 = ECIES(G-transit_pk; rc_I || P_I)`. `rc_X` is the 16-byte routing code for destination X, resolved via the table-stack mechanism (see Routing code resolution, OD3).

**Why C cannot substitute:** EncPH sits inside the token, which only V can open. ECIES is non-malleable, so C cannot swap in its own commitment. V signs the EncPH it finds *inside* the token, not a blob C supplies.

### Operation count per transaction

| Operation | Count | Notes |
| --- | --- | --- |
| ECIES encryptions | 7 | Token, P\_C, P\_F, P\_I, and three first-hop wraps. **Appendix B currently counts 4.** |
| Scalar multiplications | 14 | Each ECIES encryption = one fixed-base (ephemeral key) + one variable-base (shared secret) |
| AEAD over small inputs | 8 | EncPH, plus the symmetric part of each ECIES. Under 1,000 bytes total. |
| SHA-256 over the candidate image | 1 per image | Dominant cost: roughly 430–600 ms per 25–35 MB image at 13.7 cycles/byte, 800 MHz |
| SHA-256 over small inputs | 1 | PacketHash |

**Estimated elliptic-curve cost** on the Appendix B baseline (527,102 cycles per variable-base multiplication, Cortex-A8 at 800 MHz): 3.7M cycles (4.6 ms) if fixed-base cost is ignored, up to 7.4M cycles (9.2 ms) if fixed-base costs the same as variable-base. Precomputed fixed-base multiplication is usually cheaper, so the real figure falls in between.

**What A1 adds:** under about 5,000 cycles (about 6 µs) — one 32-byte AEAD, 64 extra bytes in the token, and 32 extra bytes in P\_C. It adds no elliptic-curve operations.

## Role selection and path disjointness

Each transaction uses nine distinct nodes across its three paths, plus the three active gatekeepers. The rules below come from paper Sections 3.2, 5 and G6, and Appendix D.6.

1. **Gatekeepers:** the three currently active gatekeepers, a known rotating set, serve every transaction. They never serve as C, F or I (D.6).
2. **C:** the device picks C at random from the device table, after excluding entries in its own validator's jurisdiction (Section 5). The routing code rc\_C is the per-transaction identifier Section 5 describes.
3. **F and I:** picked at random from the pool minus the gatekeepers, with F ≠ I. The choice must not depend on the device, manufacturer or jurisdiction, because F and I are named on the public registry record.
4. **Path disjointness (G6):** the sets {A, B, C}, {D, E, F} and {G, H, I} share no node. No node on the credential path appears on either content path.
5. **First hops:** A, D and G are distinct and are never C, F or I.

**The simulator differs from this.** The published GPA sweep (`role_rules = "distinct"`) matches: nine distinct nodes. The insider experiment (`"insider_v2"`) lets a Random hop coincide with C, F or I, and excludes only its own first hop. B can therefore be F, which puts credential-channel data at a content server. Paper Section 3.2 says that never happens, but the looser rule is deliberate, not an oversight: B never decrypts anything, so it cannot confirm the overlap even when it occurs (OD13, resolved — see Changes, A16).

The insider experiment also allows a gatekeeper to serve as a first hop. As the Addressed hop it never resolves the routing code it carries, so it never learns a packet is even destined for C, let alone which C; the payload is encrypted under C's own key, which a first hop structurally never holds. There is no shared value or resolved destination to correlate against a later PacketHash it sees as gatekeeper (OD14, resolved — see Changes, A17).

### Routing code resolution

Resolution has to give every possible Random hop the ability to resolve a code locally and offline, while denying that same ability to whichever specific server the device happened to pick as the Addressed hop for that transaction — without a live query to any third party, since a party consulted on every transaction would itself become a new, system-wide observation point (OD3, resolved — see Changes, A18).

Each server in the pool holds a **stack of tables**, one per server in the pool. The table labeled for server X contains exactly the routing lines where X is the Addressed hop, and is distributed to every server *except* X. A server's own stack is therefore the union of every other server's labeled table — every routing line in the current device table, except the lines belonging to routes where that server itself is the Addressed hop.

Resolving `rc_C` (or `rc_F`, `rc_I`) is a local, offline lookup against this stack. Whoever the device picked as the Random hop for a given path holds the table containing that path's routing line, since it is essentially never the same server as that path's Addressed hop, and resolves normally. The Addressed hop itself is the one server in the entire pool whose stack is missing precisely the table containing its own transaction's line, so it cannot resolve the code even given full access to everything it holds. This gives a cryptographic-strength guarantee from a routing property, not a policy one: there is no check to bypass, because the information simply is not present.

The cost is a stack roughly twenty times the size of a single routing table, and a rebuild of the whole stack whenever the device table or the pool composition changes. Rebuild cadence is not yet fixed; the natural candidates are gatekeeper rotation, device-table updates, or both (open sub-item under OD3).

## Per-leg message table

There are 19 legs per transaction on the wire, plus board reads by F and I. Every leg except the registry submissions is padded inside its transit encryption to a size drawn uniformly from its class: **420–460 B** for all legs except the gatekeeper fan-out, which uses **820–860 B**. Raw sizes marked \* are estimates for this spec (32-byte cred\_D, 16-byte tx\_id, 8-byte key\_ref and vk\_id); unmarked sizes are measured in `crypto_legs.py`.

| Leg | From → To | Contents | Encrypted under | Receiver learns | Raw size |
| --- | --- | --- | --- | --- | --- |
| Cred-1 | Device → A | rc\_C, P\_C | A-transit | Device IP; nothing else readable | 331 B\* |
| Cred-2 | A → B (random) | rc\_C, P\_C | B-transit | A's address; rc\_C | 331 B\* |
| Cred-3 | B → C | P\_C | C-transit | B's address; P\_C contents: Token (opaque), key\_ref, PacketHash, BK | 315 B\* |
| ContA-1 | Device → D | rc\_F, P\_F | D-transit | Device IP | 162 B |
| ContA-2 | D → E (random) | rc\_F, P\_F | E-transit | D's address; rc\_F | 162 B |
| ContA-3 | E → F | P\_F | F-transit | E's address; ContentHash, n, mod\_level | 146 B |
| ContB-1–3 | Device → G → H → I | as ContA, with rc\_I and P\_I | G-, H-, I-transit | as ContA, for I | 162 / 162 / 146 B |
| CV-1 | C → V | tx\_id, Token, key\_ref | V-transit | cred\_D, tx\_nonce, EncPH (opaque without BK) | 218 B\* |
| CV-2 (approve) | V → C | tx\_id, APPROVED, EncPH, σ\_V | C-transit | Approval and σ\_V | 181 B\* |
| CV-2 (reject) | V → C | tx\_id, REJECTED | C-transit | Rejection. **No signature.** Padded to the same class as an approval. | 69 B\* |
| GK-k (k = 1..3) | C → G\_k | PacketHash, EncPH, σ\_V, vk\_id, BK, σ\_C | Gk-term | PacketHash; manufacturer (via vk\_id); that some ring member signed | 809 B\* |
| Post-k | G\_k → Board\_k | PacketHash, σ\_C, σ\_Gk | Registry-node access only (OD2, resolved) | — | 32 + 576 + 64 B |
| Reg-F | F → Registry | ContentHash, mod\_level, σ\_F | Registry transport | ContentHash; F's identity | 97 B |
| Reg-I | I → Registry | ContentHash, mod\_level, σ\_I | Registry transport | ContentHash; I's identity | 97 B |

**Signatures:**

- `σ_V = Sign(V-sign_sk; "APPROVED" || EncPH)` — produced **only** on approval (A2).
- `σ_C = RSign(R; PacketHash)` — 576 B for a 17-member ring.
- `σ_Gk = Sign(Gk-sign_sk; PacketHash || σ_C)`.
- `σ_F = Sign(F-id_sk; ContentHash || mod_level)`, and σ\_I the same under I-id\_sk.

`tx_id` is 16 random bytes generated by C per transaction. `vk_id` identifies which V-sign\_pk to verify against; it reveals the manufacturer, which is the per-manufacturer anonymity set already stated in Section 6.3.

**Public verification** (Section 3.4) is not part of a transaction: a verifier sends a locally computed ContentHash to the registry and receives the record, if one exists.

## Checks and actions at each party

Any failed check drops the transaction and triggers that party's discard obligations. No party signs, posts or forwards after a failed check.

### Relay hops

- **Addressed hop (A, D, G):** decrypts its transit layer, reads the routing code but cannot resolve it (its own stack is missing exactly this line, see Routing code resolution), picks a random next hop (never itself), re-encrypts `rc || payload` for it, holds per the relay timing lottery, then forwards.
- **Random hop (B, E, H):** decrypts, resolves the routing code to the destination using its own table stack, holds, then forwards the payload alone under the destination's transit key.

### Credential processor C

1. Decrypts Cred-3, then P\_C. Obtains Token, key\_ref, PacketHash, BK.
2. Generates tx\_id and sends CV-1 to the validator that key\_ref designates.
3. On **REJECTED**: drops the transaction.
4. On **APPROVED**: verifies σ\_V under that validator's current V-sign\_pk, then checks that `AEAD-Dec(BK; EncPH) = PacketHash`. Either failure drops the transaction.
5. Computes `σ_C = RSign(R; PacketHash)`.
6. Sends GK-1, GK-2 and GK-3, each encrypted separately, on its staggered fan-out clock.

### Validator V

1. Decrypts CV-1, then Token. Obtains cred\_D, tx\_nonce, EncPH.
2. Checks membership of cred\_D in the key-table entry that key\_ref names.
3. Checks that tx\_nonce is not in its transaction log, then logs `(tx_id, tx_nonce)` for up to 3 years (OD5, resolved).
4. Both pass: replies APPROVED with σ\_V. Either fails: replies REJECTED with no signature.

### Gatekeeper G\_k

1. Decrypts GK-k.
2. Verifies σ\_V over `"APPROVED" || EncPH` under the V-sign\_pk named by vk\_id, and checks that key is not revoked.
3. Checks that `AEAD-Dec(BK; EncPH) = PacketHash`.
4. Verifies σ\_C against the current ring R.
5. Holds on its own hold clock (simulator: 10-second ticks, 8.33% release per tick, 5-minute cap).
6. Posts `(PacketHash, σ_C, σ_Gk)` to Board\_k.

### Content servers F and I

1. Decrypt the last content leg, then P\_F. Obtain ContentHash, n, mod\_level.
2. Compute `PH' = SHA-256(ContentHash || n)`.
3. Hold on their own node clock before checking the boards.
4. Proceed once PH' appears on at least two distinct boards, each posting with a valid σ\_Gk and a valid σ\_C against the current ring. If quorum does not form within 30 minutes, drop (OD6, resolved).
5. Submit Reg-F (or Reg-I).

### Registry

1. Verifies each submission's signature against the known server identity keys.
2. Finalizes a record once two submissions from two **distinct** identities agree on ContentHash and mod\_level.
3. Duplicate collapse: a ContentHash already on the registry is matched to the existing record, not re-posted.
4. Stamps the record with a coarsened timestamp.

## Discard and retention obligations

No party keeps any value that would let it, or a later inspector, pair one leg of a transaction with another. The only per-transaction records that survive are the validator's nonce log (with a shelf life), the board postings, and the finalized registry record.

| Party | Must discard | When | May retain | Audit |
| --- | --- | --- | --- | --- |
| Addressed hop (A, D, G) | Routing code, and any record of which code went with which packet | On forwarding | Operational logs with coarse timestamps only | Submitter-initiated routing-code sweep |
| Random hop (B, E, H) | Routing code and resolved destination for the packet | On forwarding | Same | Submitter-initiated routing-code sweep |
| C | Token, key\_ref, PacketHash, BK, tx\_id, EncPH, σ\_V | After the last GK leg is sent, or at once on rejection or failure | Nothing per transaction | PacketHash / BK / EncPH sweep |
| V | EncPH, σ\_V | After sending CV-2 | Log entry `(tx_id, tx_nonce)` for up to 3 years (OD5, resolved). **Never** stored with cred\_D, key\_ref or EncPH. | Schema attestation (Appendix C) |
| G\_k | BK, EncPH, σ\_V, vk\_id | After posting, or at once on failure | Its own posting on Board\_k | PacketHash / BK / EncPH sweep (**new:** the paper currently names only C and the board) |
| Board\_k | — | — | Postings, for 30 minutes (OD7, resolved) | — |
| F, I | n, PH', and ContentHash if not submitted | After submitting, or on quorum timeout | Nothing per transaction | Submitter-initiated n sweep (**new**) |
| Registry | — | — | Finalized record, permanently | Public |

**Audit method, unchanged from Section 6.2:** a submitter supplies ContentHash and n from their own past transaction. The governance body recomputes PacketHash and searches the named parties' logs for any residual copy. This spec adds gatekeepers and content servers to the parties searched, because both now hold values the sweep can recognize.

### Two-party combinations that correlate (outside the t = 1 claim)

Only two pairs combine cred\_D with content:

- **V + C** — linked through tx\_id or EncPH.
- **V + any one G\_k** — linked through EncPH, which V saw inside the token and G\_k receives next to PacketHash in the clear.

Paper Section 4.6, Table 3 and Section 7 currently name only V + C.

**Pairs that do not correlate:** V + F or I (no shared value without BK); C + F or I, and G\_k + F or I (a shared PacketHash, but no device identity on either side).

**Network identity (device IP)** is not device identity under the predicate f, but it is a privacy concern. Only the first hops (A, D, G) see it, and they see no content. Timing-based tracing from a first hop to a content terminal is reported in Appendix D.2.

## Registry record

A finalized record is **173 bytes**, or 205 bytes with the optional metadata hash, or 237 bytes with both the metadata hash and a parent ContentHash for an edited record. This replaces the 153-byte figure in G5, Section 5 and Section 7, which dates from the earlier single-signature design.

| Field | Size | Notes |
| --- | --- | --- |
| ContentHash | 32 B | SHA-256 of the candidate image |
| mod\_level | 1 B | Modification level (0–2 in \[4\]) |
| σ\_F | 64 B | Ed25519, F-id\_sk |
| σ\_I | 64 B | Ed25519, I-id\_sk |
| Server indices (F, I) | 2 × 2 B | Index into the registered server list, so the registry knows which keys to check at finalization (OD8, resolved) |
| Timestamp | 8 B | Posting time, coarsened |
| h(metadata) (optional) | 32 B | Enables selective disclosure without putting values on-chain |
| Parent ContentHash (optional, edits only) | 32 B | Lets holders of both images check the relationship directly, without Foundation assistance (OD10, resolved) |

The record contains no device identifier, no manufacturer identifier, and no C or gatekeeper identity. It **does** name F and I. That is safe only if F and I are chosen independently of the device, the manufacturer and the jurisdiction. State this in Section 3.3, and add F and I identities to the registry-observer row of Tables 2 and 3.

**Sibling records:** one candidate image per transaction (OD1, resolved) means a capture producing several candidate images (raw, ISP-processed, an adjustment) runs each through its own separate transaction, so their records may finalize close together. A registry observer could then link them to each other, though not to a device.

## Software-validator flow (summary; details in \[4\])

An edited image uses the same 19 legs as a capture. The roles change: the editing application is the "device", and the software developer's server is V.

**Flow:**

1. The application opens a file that verifies against the registry.
2. It tracks every tool used and its intensity until save.
3. At save, it takes patches of the original, replays the recorded tools at the recorded intensities on those patches, and compares the result against the same patches of the saved image.
4. Mismatch produces a deviation score.
5. The application submits a new transaction for the saved image. The credential packet carries a signed deviation score.

**Requirements this spec places on the flow:**

- **The parent-record reference travels only in the content channel**, never the credential channel. Otherwise V (the developer) would hold the user's license credential next to a parent ContentHash, which is a single-party correlation.
- **Patch locations are chosen unpredictably, after edits are final.** Predictable patches would let edits outside them go undetected.
- **Software credentials are not hardware-rooted.** The A\_HW extraction argument (EAL5+) does not apply. G1 is weaker for edited records than for captures, and the paper should say so in one sentence.
- **Threshold judgment is a one-party-managed tool, by necessity, not by oversight.** The developer's validator both runs the judgment software and enforces the threshold, with no independent check on that software's honesty. Co-developing judgment software with every participating developer is not tractable given the Foundation's adoption goals; the accepted mitigation is that the devkit's rules are published and auditable, not that a second party checks each judgment. This is a distinct weakness from G1's hardware-rooting gap above, not the same one restated (OD9, resolved).
